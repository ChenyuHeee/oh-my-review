# 维度：implementation-completeness（实现完整）

## 你要找什么

论文声称做了、但仓库里找不到对应实现的部分。

- 论文列出的基线，代码里没有对应实现或调用入口
- 论文报告的数据集/子任务，代码里没有加载路径
- 消融实验声称跑了 N 种配置，代码里只有其中几种可达
- 结果提取路径断裂：跑出的日志字段与论文表格里的指标对不上，或表格数字
  没有任何脚本能生成
- 关键组件是空实现、`pass`、`TODO`、或被硬编码常量替代
- 论文声称的推理/训练流程与代码实际执行路径不同（某步被跳过）

## 判定词

- CRITICAL：论文主结果依赖的实现缺失或被硬编码，数字无法由代码产生
- RECOMMENDED：非主结果的部分缺失，或提取路径需要人工拼接
- MINOR：辅助实验或可选配置缺失

## 证据契约

本维度的证据主要在代码侧，闸门2 允许只给代码侧锚定：

- `counter_source` + `counter_quote`（**必填，成对**）：逐字照抄能证明该问题
  的那一行，相对 --code-root 的路径。
  注意"缺失"也要有正面证据：引基线注册表/dispatch 分支/配置枚举里**实际存在
  的那一行**，用它说明某项不在其中。不要为了表达"不存在"而编造一行不存在的
  代码——闸门2 会逐字比对，编造的引文会被丢弃。
- `quote`（选填）：论文中声称做了该部分的原文，逐字照抄。

只给一半会被闸门2 拒绝。两者都不给的纯断言一律丢弃。

## 不要报什么

- 不要报实现存在但设计有偏，那是 design-soundness 的事
- 不要报缺 README、缺环境说明，那是 data-reproducibility 的事
- 不要把"我没找到"直接当成"不存在"；先在仓库里搜过再判断，找不到正面证据
  就不报
- 不要报未使用的实验性代码、注释掉的旧实现

## 输出

只输出 schema 规定的 JSON，不要任何解释性文字。查无问题时 `findings` 为
空数组，这是合法结果，不要为了凑数编造条目。
